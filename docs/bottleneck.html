1
_exec_sql() Blocks Flask Request Thread Critical
📍 Line 113 — workflow_manager.py ⏱ Up to 80s per call · 640s worst case 🏷 I/O · Blocking · HTTP
▼

Every Databricks SQL Statement API call sits in a synchronous 40-poll × 2 s busy-wait loop. Because Flask runs on a single WSGI thread per worker, the thread is completely blocked for up to 80 s per DDL/DML statement. init_metadata_flow() runs 8 serial DDL statements → maximum 640 s request block. All other users are frozen during this window.

Root Cause Code
# 40 polls × 2 s = 80 s max per call for _ in range(40): state = data.get("status", {}).get("state", "") if state in ("SUCCEEDED", "FAILED", ...): break time.sleep(2) # ← blocks Flask thread resp2 = s.get(...) return data
Impact
  • Flask worker frozen for up to 640 s during table creation
  • Other API requests queue behind a single long-running DDL
  • Browser shows spinner with no feedback until complete
  • 8 × serial DDL calls = maximum 640 s end-to-end
Recommended Fix
  • Run init DDLs in a ThreadPoolExecutor (parallel, not serial)
  • Return a task ID immediately; poll via a separate /status endpoint
  • Use Databricks wait_timeout=0s and poll asynchronously
2
get_metadata_status() — 8 Serial COUNT Queries Critical
📍 get_metadata_status() — workflow_manager.py ⏱ 640s worst case per dashboard load 🏷 N+1 · Dashboard · I/O
▼

The dashboard status endpoint fires one SELECT COUNT(*) per table, sequentially, for all 8 metadata tables. Each call goes through the full _exec_sql() polling loop (max 80 s). A single status page load can block the thread for up to 640 s.

Root Cause Code
# Called once per table — 8 times! for tbl in [TBL_PIPELINES, TBL_JOBS, TBL_RUNS, ...]: r = _exec_sql( f"SELECT COUNT(*) FROM {_fqn(tbl)}" ) # ↑ each is an independent blocking HTTP round-trip
Impact
  • Dashboard hangs for several seconds on every page load
  • Blocks the single Flask worker during status checks
Recommended Fix
  • Merge into a single UNION ALL query — one round trip for all 8 counts
  • Cache the result for 30 s in a module-level dict to avoid repeat calls
# Single query replaces 8 serial calls sql = " UNION ALL ".join( f"SELECT '{t}' AS tbl, COUNT(*) AS cnt FROM {_fqn(t)}" for t in ALL_TABLES )
3
full_sync_to_dbr() — Unbounded Serial MERGE Loop Critical
📍 full_sync_to_dbr() — workflow_manager.py ⏱ 400+ round trips for 100-table migration 🏷 N+1 · Bulk · MERGE
▼

full_sync_to_dbr() iterates over every pipeline, job, run and watermark and fires one individual MERGE statement each. For 100 source tables (300 jobs, 50 runs, 100 watermarks), that is 550+ sequential HTTP calls. No batching, no parallelism.

Root Cause Code
for gid, grp in PIPELINE_GROUPS.items(): _sync_pipeline_to_dbr(grp) # 1 MERGE for jid, job in JOB_REGISTRY.items(): _sync_job_to_dbr(job) # 1 MERGE each for rid, run in JOB_RUNS.items(): _sync_run_to_dbr(run) # 1 MERGE each
Impact
  • Full sync hangs the UI for minutes when many tables exist
  • Grows proportionally with number of pipelines — O(n) HTTP calls
  • No progress feedback during the operation
Recommended Fix
  • Build a multi-row VALUES clause — one MERGE for all pipelines
  • Run pipeline/job/run syncs in parallel using ThreadPoolExecutor
  • Return a background task ID and report progress via SSE or polling
4
sync_source_tables_to_dbr() — Row-by-Row INSERTs High
📍 sync_source_tables_to_dbr() — workflow_manager.py ⏱ 1 HTTP call per table row 🏷 N+1 · INSERT · Unbatched
▼

When source tables are discovered and synced to Databricks, each table fires a separate INSERT INTO wf_source_tables VALUES (...). For a schema with 200 tables, this creates 200 sequential HTTP round-trips to the Databricks SQL Statement API.

Root Cause Code
for t in tables: # one loop = one INSERT sid = uuid4().hex[:12] sql = f"INSERT INTO {_fqn(TBL_SOURCES)} VALUES ({_esc(sid)}, ...)" _exec_sql(sql) # ← blocking call per row
Impact
  • 200-table schema sync can take several minutes
  • API rate-limit risk on large databases
Recommended Fix
  • Build a single INSERT with a multi-row VALUES clause
  • Chunk into batches of 500 rows to stay within SQL statement size limits
# Build one INSERT for all rows values = ", ".join( f"({_esc(uuid4().hex[:12])}, {_esc(t['table'])}, ...)" for t in tables ) _exec_sql(f"INSERT INTO {_fqn(TBL_SOURCES)} VALUES {values}")
5
O(n) Scan in _poll_databricks_run() Every 10 Seconds High
📍 _poll_databricks_run() — workflow_manager.py ⏱ Grows with every run stored in JOB_RUNS 🏷 Linear scan · Lock contention · Background thread
▼

The Databricks run poller iterates over the entire JOB_RUNS dict on every 10-second tick to find runs matching a specific dbr_run_id. With multiple concurrent pipeline runs, multiple poller threads each do a full O(n) scan of all accumulated run records — while holding _lock.

Root Cause Code
# Every 10s, iterates ALL JOB_RUNS with _lock: for rid, run in JOB_RUNS.items(): if str(run.get("dbr_run_id")) == dbr_run_str \ and run["job_id"] in grp_job_ids: # update this run
Impact
  • Lock held during full linear scan — blocks all write operations
  • Multiple simultaneous poller threads amplify contention
  • Gets worse over time as JOB_RUNS grows unboundedly
Recommended Fix
  • Add a secondary index: DBR_RUN_INDEX = {dbr_run_id: [local_run_ids]}
  • Populate index at run creation; look up directly instead of scanning all runs
  • Release lock before Databricks HTTP call; only lock during write
6
Single Global _lock — Coarse-Grained Contention High
📍 _lock = threading.Lock() — module level ⏱ Serialises all reads and writes across all stores 🏷 Lock contention · Threading · Concurrency
▼

A single threading.Lock() protects all in-memory stores: JOB_REGISTRY, JOB_RUNS, WATERMARKS, and PIPELINE_GROUPS. Background poller threads, the scheduler thread, and every Flask request handler compete for the same lock — even when they access completely independent data structures.

Root Cause Code
# ONE lock for everything _lock = threading.Lock() # Used by: Flask handlers, poller threads, # scheduler thread, bulk create, delete... with _lock: JOB_REGISTRY[jid] = job JOB_RUNS[rid] = run WATERMARKS[tbl] = wm PIPELINE_GROUPS[gid] = grp
Impact
  • Background threads block user-facing requests mid-update
  • Long bulk-create operation starves poller and scheduler
  • Cannot read while writing even to different data structures
Recommended Fix
  • Use threading.RLock() per store: _job_lock, _run_lock, _wm_lock
  • Replace with threading.RWLock (readers-writer lock) for read-heavy paths like list_jobs()
  • Consider collections.deque with maxlen for append-only logs — no lock needed
7
load_metadata_from_dbr() Loads Full JSON Logs on Re-connect High
📍 load_metadata_from_dbr() — LIMIT 200 runs ⏱ Potentially 2MB+ on reconnect 🏷 Memory · N+1 · Hydration
▼

On every reconnect or server restart, load_metadata_from_dbr() fetches 200 run records including full JSON log arrays (each log entry is a timestamped string). A run with 50 log lines of 100 characters each = 5 KB. 200 runs = up to 1 MB of JSON parsed and kept in memory — for data that is mostly display-only.

Root Cause Code
# Fetches 200 rows including full logs JSON r = _exec_sql( f"SELECT * FROM {_fqn(TBL_RUNS)}" " ORDER BY started_at DESC LIMIT 200" ) # Each row parses the "logs" JSON column logs = json.loads(logs_raw)
Impact
  • Startup hydration is slow — logs parsed for every run
  • Memory grows proportionally with log verbosity
  • All 200 runs kept in RAM even if 190 are never displayed
Recommended Fix
  • Exclude the logs column from the hydration SELECT — load logs lazily per run
  • Add a GET /run/{id}/logs endpoint that fetches logs on demand only
  • Reduce LIMIT from 200 to 50 for in-memory hydration; paginate from DB for history
8
Blocking HTTP Call at Module Import Time Medium
📍 _restore_from_deploy_config() — called at module load ⏱ Up to 15s startup delay if Databricks is unreachable 🏷 Startup · Blocking HTTP · I/O
▼

_restore_from_deploy_config() is called at module level (not inside a function). It issues a synchronous GET /api/2.0/sql/warehouses request during import. If Databricks is slow or unreachable, Flask startup blocks for up to the 15-second timeout before the app begins serving requests.

Root Cause Code
# At the bottom of the module — runs at import _restore_from_deploy_config() # Inside it: resp = s.get( f"{_dbr_host}/api/2.0/sql/warehouses", timeout=15 # ← 15s block during startup )
Impact
  • App takes 15+ seconds to start if Databricks is down
  • Gunicorn/uWSGI worker startup timeout may kill the process
  • Cold-start in Docker containers is unreliable
Recommended Fix
  • Move warehouse discovery to a lazy background thread started from app.py
  • Use a 3-second timeout with silent failure; retry on first API use
  • Cache warehouse ID in deployconfig.json to skip discovery on re-start
9
JOB_RUNS Unbounded Memory Growth — No TTL or Eviction Medium
📍 JOB_RUNS = OrderedDict() — module level ⏱ Grows indefinitely across server uptime 🏷 Memory leak · In-process · OrderedDict
▼

JOB_RUNS is an OrderedDict with no maximum size or TTL policy. Every run_job() call appends an entry. After days of running, hundreds of completed runs (each with full log arrays) accumulate in memory, consuming RAM and slowing down every linear scan over the dictionary.

Root Cause Code
# Never evicted. Grows forever. JOB_RUNS = OrderedDict() # Every run adds a new entry: with _lock: JOB_RUNS[run_id] = run # no maxlen, no TTL
Impact
  • Memory grows without bound during long server uptime
  • O(n) operations (list_runs, poller scan) slow down gradually
  • Risk of OOM on servers with limited RAM after heavy use
Recommended Fix
  • Cap at last 500 runs: evict oldest when limit is reached (FIFO via OrderedDict.popitem(last=False))
  • Add a TTL: evict runs older than 7 days in the background scheduler tick
  • Move completed runs to Databricks-only storage; serve history endpoint from Delta query
10
Bulk Simulated Runs Spawn N Threads Simultaneously Low
📍 run_pipeline_group() / create_pipelines_bulk() — workflow_manager.py ⏱ N threads spawned instantly for N tables 🏷 Thread storm · Resource contention · Demo mode
▼

When bulk-running pipelines in simulated mode, run_pipeline_group() calls run_job() for each job which spawns a daemon=True thread immediately. For a 100-table bulk run, this creates up to 300 threads simultaneously (3 jobs per table), all sleeping and competing for — and repeatedly acquiring — _lock.

Root Cause Code
# Each call spawns a thread immediately for jid in grp.get("job_ids", []): r = run_job(jid) # ← spawns 1 thread run_results.append(r) # 100 tables × 3 jobs = 300 threads at once
Impact
  • Thread storm on large table sets degrades all operations
  • GIL contention in CPython compounds the problem
  • All threads contend for the same global _lock
Recommended Fix
  • Add a threading.Semaphore(max_concurrent=10) around thread spawning
  • Use a producer-queue pattern: one worker pool processes runs in controlled batches
  • Consider concurrent.futures.ThreadPoolExecutor(max_workers=8) for managed execution

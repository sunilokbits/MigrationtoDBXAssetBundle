Prerequisites
⚡
Step 0 — Enable Change Tracking on Azure SQL
One-time manual setup on your source database
⚠️
Manual Step: Change Tracking must be enabled on the database and each table before the CDC pipeline can pull incremental changes.

1. Enable Change Tracking on the Database:

ALTER DATABASE [YourDatabase]
SET CHANGE_TRACKING = ON
(
    CHANGE_RETENTION = 3 DAYS,      -- How long CT data is kept
    AUTO_CLEANUP = ON               -- Automatically purge old CT records
);

2. Enable Change Tracking on Each Table:

ALTER TABLE [dbo].[Employees]
ENABLE CHANGE_TRACKING
WITH (TRACK_COLUMNS_UPDATED = ON);  -- Tracks which columns changed

ALTER TABLE [dbo].[Departments]
ENABLE CHANGE_TRACKING
WITH (TRACK_COLUMNS_UPDATED = ON);

3. Verify Change Tracking is Active:

-- Check database-level CT
SELECT DB_NAME(database_id) AS db_name, is_auto_cleanup_on, retention_period
FROM sys.change_tracking_databases;

-- Check table-level CT
SELECT OBJECT_NAME(object_id) AS table_name, is_track_columns_updated_on
FROM sys.change_tracking_tables;

-- Get current CT version
SELECT CHANGE_TRACKING_CURRENT_VERSION() AS current_version;

🔁 Subsequent Runs — Incremental CT

Reads stored version 42 → uses CHANGETABLE to get only changes.

SELECT T.*, 
  CT.SYS_CHANGE_OPERATION AS __cdc_operation,
  CT.SYS_CHANGE_VERSION   AS __cdc_version
FROM CHANGETABLE(
    CHANGES [dbo].[Employees], 42
  ) AS CT
INNER JOIN [dbo].[Employees] AS T
  ON CT.[EmployeeID] = T.[EmployeeID]
WHERE CT.SYS_CHANGE_OPERATION
  IN ('I', 'U')
✅
Returns only changed rows since version 42. Updates CT version to latest.

Stage 2 — Bronze
🥉
02_Meta_Bronze.py — DLT Bronze with Quality Expectations
Reads Parquet from Landing, validates, writes Bronze Delta with CDF enabled
# When exec_mode = "dlt"
import dlt

@dlt.table(
    name="bronze_Employees",
    comment="Bronze — raw ingestion with DLT quality expectations",
    table_properties={
        "quality": "bronze",
        "delta.autoOptimize.optimizeWrite": "true",
        "delta.enableChangeDataFeed": "true",  # ← CDF enabled!
    },
)
@dlt.expect_or_drop("__valid_landing_ts", "__landing_ts IS NOT NULL")
@dlt.expect("__has_batch_id", "__batch_id IS NOT NULL")
@dlt.expect("__has_source", "__source_table IS NOT NULL")
def bronze_dlt_table():
    df = spark.read.parquet("/mnt/landing/Employees")
    return (df
        .withColumn("__bronze_ts", F.current_timestamp())
        .withColumn("__source_table", F.lit("dbo.Employees"))
        .withColumn("__is_quarantined", F.lit(False)))

Stage 3 — Silver (SCD Type 1 Merge)
🥈
03_Meta_Silver.py — dlt.apply_changes() for CDC Merge
SCD Type 1 MERGE: Inserts, Updates, and Deletes automatically applied
# When exec_mode = "dlt" AND cdc_mode = "change_tracking"
import dlt

# 1. Create target streaming table
dlt.create_streaming_table(
    name="silver_Employees",
    comment="Silver — CDC merge via Change Tracking",
    table_properties={
        "quality": "silver",
        "delta.autoOptimize.optimizeWrite": "true",
        "delta.enableChangeDataFeed": "true",
    },
)

# 2. Define the CDC merge logic
dlt.apply_changes(
    target = "silver_Employees",           # Target table
    source = "bronze_Employees",           # Source (Bronze DLT table)
    keys   = ["EmployeeID"],               # Primary Key for MERGE
    sequence_by = F.col("__bronze_ts"),    # Ordering for late-arriving data
    apply_as_deletes = F.expr(             # Delete condition
        "__cdc_operation = 'D'"
    ),
    except_column_list = [                 # Columns to drop
        "__landing_ts", "__load_type",
        "__is_quarantined",
        "__cdc_operation", "__cdc_version",
        "__cdc_mode", "__batch_id",
        "__bronze_version",
    ],
)

How apply_changes() Works

1. Read source (Bronze) table
DLT reads bronze_Employees using dlt.read() — gets all new/changed rows including CDC audit columns.
2. Match rows by primary key
Uses keys = ["EmployeeID"] to join incoming rows against existing Silver table. This performs a MERGE operation.
3. Order by sequence column
sequence_by = __bronze_ts ensures that if multiple changes for the same key arrive, only the latest wins (handles late-arriving data).
4. Apply operations
INSERT (I): Key not found in Silver → new row inserted
UPDATE (U): Key exists → row overwritten (SCD Type 1)
DELETE (D): Matched by apply_as_deletes expression → row removed
5. Strip audit columns
except_column_list removes internal CDC/audit columns so the Silver table contains only clean business data.

Version Update Logic (Extract Notebook)

# After successful extraction, fetch latest CT version from SQL Server
ct_ver_query = "(SELECT CHANGE_TRACKING_CURRENT_VERSION() AS ct_ver) AS ctv"
ct_ver_df = spark.read.jdbc(jdbc_url, ct_ver_query, properties=jdbc_props)
new_ct_ver = str(ct_ver_df.collect()[0]["ct_ver"])

# MERGE into watermark table (insert or update)
spark.sql(f"""
    MERGE INTO {wm_tbl} AS t
    USING (SELECT '{FULL_TABLE}' AS table_name,
                  '{new_ct_ver}' AS last_value) AS s
    ON t.table_name = s.table_name
    WHEN MATCHED THEN UPDATE SET t.last_value = s.last_value
    WHEN NOT MATCHED THEN INSERT *
""")

CDC Mode vs DLT Execution Mode — What's the Difference?
Two independent settings that control different parts of the pipeline
💡
Key Insight: CDC Mode controls how data is extracted from SQL Server. DLT Execution Mode controls how data is processed in Databricks. They are independent — you can mix and match them.
CDC Mode cdc_mode
How Data is Extracted

Controls the SQL query used by 01_Meta_Extract.py to pull data from Azure SQL Server into the Landing Zone.

🔸 Watermark (Classic)
Uses a date/ID column to track "last extracted" position

🔹 Change Tracking (CT)
Uses SQL Server's built-in CT system to get exact I/U/D operations
SELECT T.*, CT.SYS_CHANGE_OPERATION
FROM CHANGETABLE(CHANGES [Employees], 42) CT
INNER JOIN [Employees] T ON CT.ID = T.ID

Frequently Asked Questions
What if Change Tracking retention expires?
If the stored CT version is older than the CHANGE_RETENTION period, SQL Server returns an error. The pipeline will fall back to a full load and reset the CT version. Set CHANGE_RETENTION high enough to cover your pipeline schedule (e.g., 3-7 days).
Can I use different primary keys per table?
Yes. When creating pipelines in bulk, each table can override the global primary_keys in its source_config. The notebook reads source_config.get("primary_keys", []) per-job from wf_job_metadata.
Why both CDF and apply_changes?
Change Data Feed (CDF) on Bronze/Silver tables allows downstream consumers to read only changes (e.g., Gold layer, BI tools). apply_changes is how the Silver layer processes CDC data from Bronze — they serve different purposes and complement each other.
What's the difference between CDC Mode and DLT Execution Mode?
CDC Mode (cdc_mode): Controls how data is extracted from SQL Server — either classic watermark-based or Change Tracking.
DLT Execution Mode (exec_mode): Controls how Bronze/Silver notebooks process data — either standard PySpark write or DLT decorators.
You can use CT extraction with standard PySpark mode (no DLT), but DLT + CT gives you the full apply_changes() SCD merge capability.
How do Deletes work if they're excluded from the INNER JOIN?
The extract query uses WHERE SYS_CHANGE_OPERATION IN ('I','U') because deleted rows no longer exist in the source table (so INNER JOIN returns nothing). To capture deletes, you'd add a separate query for SYS_CHANGE_OPERATION = 'D' using only the CT columns — the pipeline's apply_as_deletes expression in Silver then removes matching rows by primary key.
